  四、面试题回答（以项目为证据）
============================================================

  Q：上下文工程是怎么设计的？
    在项目里，每个 Agent 节点只接收它需要的信息。method_node 只读 methodology 章节的
    字符范围，不把全文塞进去。具体实现是每个节点返回 {**state, 'new_key': value}，
    精确控制下游节点的上下文范围，节省 token，减少噪声干扰。

  Q：记忆机制是怎么做的？
    两层记忆设计。短期记忆：LangGraph state 在节点间传递，执行完自动清理；
    长期记忆：eval_results.json 持久化存储每次评测结果（论文名/评分/原因/时间戳）。
    下次批量运行时读取历史跳过已评测论文，不重复消耗 API 费用。

  Q：Agent 的任务规划是怎么做的？（ReAct、Plan-and-Execute）
    两种都有体现。7节点流水线是 Plan-and-Execute：先规划好执行顺序再依次执行，
    每步结果传递给下一步。低分重试闭环是 ReAct：judge 打分（观察）→
    生成改进指令（思考）→ 执行模型重做节点（行动）→ 再打分（观察），循环最多两次。

  Q：Modular Agent 多步规划具体怎么做？
    执行与评测完全分离：llm_executor（gpt-4o-mini）负责读论文提取信息，
    llm_judge（gpt-4o）负责评估输出质量。好处一：避免自评偏差；
    好处二：成本控制，执行用便宜模型，评测用准确模型。
    每个节点独立，某个技能失败只重做那个节点，不影响其他节点结果。

  Q：如何设计一套评估方案判断 AI 系统好不好？
    Skill Rubric 方案：6个维度独立评分（0~1），五档标准（1.0/0.75/0.5/0.25/0.0），
    不是模糊打分。用更强的模型（gpt-4o）作 judge，防止自评偏差。
    结果写入 Excel 可横向对比多篇论文。
    实测：22篇论文，skill4 通过重试从0.25提升到1.00，验证闭环有效。

  Q：如何提升相关度/优化回答效果？
    低分触发反馈重试。judge 不只给分，还给出具体改进指令，
    如'没有列出 baseline 名字，重提取时必须明确写出对比方法名称'。
    执行模型针对性重做，不是盲目重跑全部。
    今天实测：skill5 因连接错误得0.00，重试后恢复0.75，容错机制有效。

  Q：高频请求延迟高怎么优化？
    arXiv API 触发429限速后，实现指数退避重试：5s → 10s → 20s → 40s。
    原理与滑动窗口限流一致，检测到限速就主动降低请求频率，不是一直重试雪崩。
    查询之间固定等待3秒，下载之间等待1秒，从源头控制速率。

  Q：是否使用过 LangChain 等 Agent 框架？
    使用 LangGraph（LangChain 生态）构建 StateGraph，7节点有向图，
    支持 MemorySaver checkpointer 断点续跑。
    相比 LangChain 的 AgentExecutor，LangGraph 更适合多步骤有状态的 Agent 流程，
    节点间数据流更清晰，便于调试和局部重试。

── Embedding 方案：双轨并行（待决策） ──

方案A：OpenAI API（text-embedding-3-small）
  优点：效果好、调用简单、与现有 API key 复用
  缺点：联网依赖、每次调用有费用（很便宜，$0.02/1M tokens）

  候选模型：
    - all-MiniLM-L6-v2（英文，轻量，384维，~90MB）

  优点：完全离线、无费用、可自己微调
  缺点：需要安装依赖（sentence-transformers + torch），首次下载模型较大
  适合：离线环境、面试展示"我了解本地模型"的技术深度

  八、学习笔记：向量检索原理 × 面试应对 × 工业实景
============================================================

【核心问题】为什么 FAISS 索引要配一个 meta 文件？
─────────────────────────────────────────────
  FAISS 只存向量数字，不存任何文字信息。

  paper_index_local.faiss
    内容：[0.12, -0.34, 0.56, ...] × N 篇论文
    能回答："第 3 个向量和查询最像"
    不能回答："第 3 个是哪篇论文"

  paper_meta.json
    内容：第0篇 = xxx论文，质量分 = 0.75，评语 = "..."
    作用：把向量编号翻译回有意义的论文信息

  两个文件是"索引"和"字典"的关系，缺一个都没法用。

  记忆口诀：FAISS 认数字，meta 认名字，合体才能说人话。


【面试怎么问，怎么答】
─────────────────────────────────────────────
  面试不考手写 FAISS，考的是你对原理的理解。

  常见问法：
    Q: 向量检索用的什么库？
    Q: 索引和元数据为什么分开存？
    Q: 向量维度怎么选？
    Q: 千万级向量怎么保证低延迟？

  你现在的项目能回答前两个。后两个是进阶问题，知道方向就行。

  万能回答模板（背下来）：
  ┌─────────────────────────────────────────────────────┐
  │ "我用 FAISS IndexFlatIP 做了精确余弦检索，          │
  │  知道它在向量量级大了之后要换 HNSW，                │
  │  这是我下一步要优化的方向。"                        │
  └─────────────────────────────────────────────────────┘
  这句话的价值：说明你知道自己在做什么，也知道局限在哪。
  面试官最怕候选人"只会用，不知道为什么"。


【工业实景对照表】
─────────────────────────────────────────────

  规模          向量库                    元数据        检索方式
  ──────────────────────────────────────────────────────────
  学习项目      FAISS 本地文件            JSON 文件     IndexFlatIP（精确）
  小公司        FAISS / Milvus 单机       MySQL         IndexFlatIP / IVF
  中大厂        Milvus 集群 / Pinecone    Elasticsearch HNSW（近似，快100倍）
  超大厂        自研向量引擎              分布式存储    ANN + 过滤条件混合

  核心演进规律：
    数据量小 → 精确搜索（IndexFlatIP），准确率100%，速度够用
    数据量大 → 近似搜索（HNSW/IVF），牺牲1%~5%准确率，换取100倍速度


【关键概念速查】
─────────────────────────────────────────────
  IndexFlatIP   暴力内积搜索，精确，数据量大时慢
  HNSW          Hierarchical Navigable Small World，近似搜索，工业主流
  IVF           Inverted File Index，先聚类再搜索，中等规模常用
  余弦相似度    向量归一化后的内积，衡量语义相似程度（值越接近1越像）
  归一化        向量除以自身模长，使所有向量长度为1，内积等价余弦

  本项目用法：embedding 生成时做归一化 → FAISS 用 IndexFlatIP（内积）
              = 实际上在做余弦相似度检索

── 中文化方案讨论 ──

  问题：eval_results.json 里的提取内容（research_question/methodology/
        datasets/results/critique）全是英文，前端显示不友好。

  讨论过的方案：
    1. 改 prompt 让 executor 直接输出中文
       → 不影响 judge（gpt-4o 多语言），但需重跑全部论文
    2. 加翻译接口，实时翻译
       → 每次请求多一次 GPT 调用，慢且持续花钱
    3. 最终方案：在流水线末尾加 translator 节点，英文→中文一次性翻译后存入 json
       → 现有7个节点完全不动，judge 读英文打分不受影响，json 存中文供前端显示

  BM25 中文检索问题：
    BM25 按空格分词，对中文失效，需要引入 jieba 分词库（后续处理）
    向量检索用英文建索引，但用户输入中文查询时需要先翻译成英文再检索

── 多用户规模规划（核心决策）──

  目标：支持 1000 个中文用户同时使用

  规模对应方案：
    100人：实时翻译查询（中文→英文），每次调用GPT，慢但够用
    1000人：加查询缓存（Redis），相同查询只翻译一次，延迟从2s降到50ms
    几十万人：建双语索引（中文索引+英文索引），按用户语言路由

  1000人落地方案（已定）：
    Step 1：流水线加 translator 节点，json 存中英双版本
    Step 2：索引继续用英文建（text-embedding-3-small 英文语义空间更准）
    Step 3：用户输入中文查询 → 先翻译成英文 → 检索 → 返回中文内容
    Step 4：加 Redis 缓存常见查询，避免重复翻译
    核心原则：检索质量（英文索引）和用户体验（中文显示）分开处理

  下一步行动：
    1. 在 LangGraph 流水线末尾加 translator 节点（第8个节点）
    2. 对44篇已有数据补跑翻译（只翻译，不重新评测，省钱）
    3. 重建 FAISS 索引（索引内容不变，还是英文）

    BM25 用中文内容建语料，但英文分词（按空格切）对中文无效
    影响：中文关键词查询时 BM25 召回率下降
    解决：引入 jieba 中文分词（后续处理，不影响向量检索）

  【后果2：FAISS 索引需要重建】
    现在索引是用英文内容建的，翻译后内容变了，索引和 json 不一致
    影响：如果不重建索引，检索结果和显示内容会对不上
    解决：翻译完之后重跑 build_index.py，但索引仍用英文原文建
          （json 存中文显示，索引用英文检索，两套独立）
    注意：需要在 eval_results.json 里同时保留英文原文字段备用

  【后果3：已有44篇数据需要补跑】
    现有44篇 json 里没有中文内容，需要对这44篇单独跑翻译
    费用估算：44篇 × 5字段 × 平均500字 ≈ 约 $1~2
    时间估算：约15~30分钟
    优点：不需要重新评测，只翻译，不消耗 judge 调用

  【后果4：测试用例可能需要更新】
    test_search_bm25_keyword.py 里的查询是英文的
    翻译后语料变中文，BM25 测试用例需要对应改成中文查询
    向量检索测试不受影响（索引还是英文）

  【无影响部分】
    Skill Rubric 打分：judge 读的是英文原文，不读翻译后内容，完全不受影响
    skill_scores / skill_reasons：这些字段是分数和英文原因，不翻译
    论文质量分（paper_quality_score）：不受影响
    FAISS 向量索引：继续用英文建，不受影响

── 中文查询怎么变成英文检索（2026-04-02 讨论）──

  完整链路：

    用户前端输入：对比学习 冷启动
          ↓
    前端发送中文查询给 FastAPI（api_server.py）
          ↓
    api_server.py 收到后，调一次 GPT 翻译：
      "把以下查询翻译成英文：对比学习 冷启动"
      → "contrastive learning cold start"
          ↓
    用英文查询去查 FAISS 索引（英文 embedding 空间）
          ↓
    找到相关论文，读取中文字段（research_question_cn 等）
          ↓
    把中文内容返回给前端显示

  用户感知：输入中文 → 看到中文结果
  实际发生：中文查询 → 英文检索 → 中文展示

  为什么不直接用中文查英文索引：
    FAISS 索引是用英文内容建的，英文 embedding 语义空间更准确。
    直接用中文查询去查英文索引，两种语言的向量方向不对齐，
    语义对不上，召回效果会明显变差。
    翻译这一步就是为了让查询和索引在同一个语义空间里。

  维护两套内容的含义：
    json 里同一篇论文存两个版本：
      "research_question":    "The paper addresses..."   ← 英文，建索引用
      "research_question_cn": "本文研究了..."            ← 中文，前端显示用
    检索走英文，显示走中文，各司其职，互不干扰。

  Redis 缓存的作用（1000人规模）：
    每次查询都调 GPT 翻译会慢（约1~2秒）且花钱。
    加缓存后：
      第一次查"对比学习冷启动" → 翻译 → 存入 Redis
      之后再查同样的词 → 直接从 Redis 取，50ms 返回
    相同查询只翻译一次，大幅降低延迟和费用。

── 中文化实施过程 Q&A（2026-04-02）──

  Q：translator 节点是干什么的？和 Excel 有关吗？是 Agent 的一部分吗？
  A：translator 是 LangGraph 流水线的第8个节点，评测完自动把英文内容翻译成中文
     存入 eval_results.json（_cn 字段）。Excel 导出时读这些字段，所以 Excel 也变中文。
     是 Agent 流水线的一部分，和其他7个节点地位相同。

  Q：翻译成中文之后会和 Rubric 打分冲突吗？
  A：不会。scorer（打分）在 translator（翻译）前面，judge 读的永远是英文原文。
     顺序保证了两件事互不干扰。

  Q：维护两套是什么意思？
  A：json 里同一篇论文存两个版本：
     "research_question"    英文，建 FAISS 索引用（检索质量更好）
     "research_question_cn" 中文，前端显示用
     两套各司其职，检索走英文，显示走中文。

  Q：用户前端输入中文，怎么变成英文去检索的？
  A：api_server.py 收到中文查询后，先调 GPT 翻译成英文，再去查 FAISS 索引，
     找到结果后读中文字段返回给前端。用户感知不到中间发生了翻译。

  Q：translate_existing.py 是改索引吗？
  A：不是。是翻译 eval_results.json，把44篇已有数据补上 _cn 中文字段。
     三个文件区别：
       translate_excel.py     → 翻译 Excel（给自己看）
       translate_existing.py  → 翻译 json（给前端用）
       build_index.py         → 改索引（检索用，现在不动）

  Q：为什么前端要读 json，不能读 Excel？
  A：用户搜索流程是：查 FAISS 索引 → 读 json → 返回前端显示。
     Excel 是给人看的表格，json 是给程序读的数据，两个来源不同。
     要让前端显示中文，必须把 json 也翻译。

  Q：FastAPI 是从 Excel 里读数据吗？
  A：不是。FastAPI 从 eval_results.json 读数据，Excel 只是给自己用 Office 打开看的。
     两个完全独立，FastAPI 根本不认识 Excel 文件。
     所以翻译 Excel 对前端没有任何影响，要让前端显示中文必须翻译 json。

  Q：json 里有这么多数据吗？
  A：有，而且比 Excel 更全。json 是数据的源头，Excel 是 json 的"视图"。
     每条记录包含：paper / paper_quality_score / skill_rubric_total /
     research_question / methodology / datasets / results / critique /
     skill_scores（6个维度分数）/ skill_reasons / comment
     44篇论文全部存在 data/eval_results.json，FastAPI 读这个返回给前端。

  Q：索引是怎么用的？
  A：用户搜索时，查询词转成向量，和 FAISS 索引里44篇的向量逐一比较，
     找出最相似的几篇，再去 json 里读这几篇的详细内容返回给前端。
     FAISS 只负责"找到哪几篇"，json 负责"内容是什么"，缺一不可。

  Q：是不是有很多索引？BM25 和 embedding 都是索引吗？
  A：对，确实有两个索引：

     FAISS 索引（向量索引）
       文件：data/paper_index_api.faiss
       存的：每篇论文内容转成的1536维向量
       用途：语义检索，能理解近义词和语义相近的表达
       特点：提前建好存成文件，不会自动更新

     BM25（关键词索引）
       文件：没有单独文件，每次搜索时实时从 json 构建
       存的：每篇论文的词频统计
       用途：专有名词精确匹配（如 NeuralUCB、CL4SRec）
       特点：每次搜索实时计算，json 改成中文后自动就是中文索引

     两个索引配合使用（混合检索）：
       0.7 × FAISS分数 + 0.3 × BM25分数 = 最终排名

     结论：json 翻译成中文后，BM25 自动变中文，不需要额外操作。
           只有 FAISS 是提前建好的文件，现在暂时不动（继续用英文）。

  当前进度：
    translate_excel.py 正在跑（翻译44篇 Excel，给自己看用）
    下一步：跑 translate_existing.py（翻译 json，给前端用）
    再下一步：改 api_server.py 返回中文字段，前端自动显示中文

============================================================
  十五、搜索质量问题诊断与改进方案（2026-04-05）
============================================================

── 实测问题（4个核心缺陷）──

【问题1：数据质量污染（最严重）】
  现象：搜索 "graph neural network" 返回流体力学、图论数学论文
  根因：爬取时虽加了 cs 分类过滤，但作者把无关论文挂在 cs.LG 下
  工业做法：建索引前用分类器做领域过滤，保证语料库纯净
  原则：Garbage in, Garbage out

【问题2：归一化制造虚假信心】
  现象：cold start 搜索返回 "S-packing chromatic" 数学论文，score=0.483
  根因：归一化是相对的，最高分永远是1.0，低质量匹配也显得"不错"
  工业做法：设绝对阈值（cosine < 0.3 直接过滤），宁可返回空结果

【问题3：缺少 Rerank 精排层】
  现状流程：召回（BM25+FAISS）→ 直接返回
  工业流程：召回（BM25+FAISS，top-50）→ Cross-Encoder精排 → 返回top-5
  Bi-Encoder vs Cross-Encoder：
    Bi-Encoder：查询和文档分别编码，快，精度中等（用于大规模召回）
    Cross-Encoder：查询+文档联合打分，慢，精度高（用于小范围精排）
  工业案例：Google、Bing、各大电商标准两阶段检索架构

【问题4：Embedding 内容质量不均匀】
  现状：用 AI 提取的结构化字段（research_question 等）建向量
  问题：部分论文提取质量差，字段内容短，向量信息量不足
  工业做法：用论文摘要（Abstract）+ 标题建索引，原始信息更稳定

── 改进优先级 ──

  P0（立刻，一天内）：
    1. 加相似度绝对阈值过滤（score < 0.3 不返回）
    2. 清洗数据库，删除无关领域论文（物理/数学/流体力学）

  P1（本周）：
    3. 加 Cross-Encoder Rerank（sentence-transformers 有现成模型）
    4. 用 PDF 摘要替代 AI 提取字段做 Embedding

  P2（上线后）：
    5. 用户点击行为做相关性反馈，自动优化排序
    6. 查询扩展（短查询补充同义词）

── 核心结论 ──
  搜索质量问题根源不是算法，是数据。
  先清洗语料库，删掉无关论文，搜索质量会立刻大幅提升。
  算法再好，喂垃圾数据，结果也是垃圾。

  Step 12：Pipeline 五大问题诊断与修复（2026-04-06）
============================================================

── 背景 ──
  在当前 164 篇论文规模上，对搜索 Pipeline 做了系统性诊断。
  发现五个贯穿 数据 → 索引 → 检索 → 排序 → 评估 全链路的问题。
  核心结论：最大的问题不是算法是数据。

── 五个问题及根因 ──

  P1 数据清洗：语料库污染
    现象：搜 "GNN node classification" 返回流体力学论文（分数 0.61，看似合理）
    根因：上传时无领域校验；build_index.py 全量建索引不过滤
          向量空间里 "graph of mesh nodes"（流体）与 GNN 的 "graph nodes" 距离很近
    修复：is_cs_paper() + _CS_KEYWORDS 白名单（32个 CS/AI 关键词）
          load_records() 建索引时过滤非目标领域论文

  P2 Embedding 质量：GPT 压缩摘要
    现象：两篇用不同方法解同一问题的论文，向量距离接近零（被认为是近似重复）
    根因：build_text() 用 GPT 提取的结构化字段（300词→60词，信息量损失80%）
          "GraphSAGE with mean aggregator" → "graph sampling method"（泛化）
    修复：build_text() 优先使用 abstract（原始摘要）；无摘要时降级 GPT 字段
          db.py 新增 abstract 列（ALTER TABLE 自动迁移）

  P3 缺精排：Bi-Encoder 无法精确排序
    现象：top-10 里第3名和第8名分数差0.03，但相关性天壤之别
    根因：Bi-Encoder（text-embedding-3-small）训练目标是快速召回，不是精排
    修复：rerank_with_cross_encoder()，使用 cross-encoder/ms-marco-MiniLM-L-6-v2
          架构：Bi-Encoder 召回 top-50 → CrossEncoder 精排 → 返回 top-k
          延迟加载：首次 ~300ms，支持 CPU，~80MB
          降级：CrossEncoder 不可用时原样返回 Bi-Encoder 结果

  P4 缺评估兜底：相对归一化掩盖低质量
    现象：搜索完全无关领域，原始最高分 0.08，归一化后变成 1.0，误报高相关
    根因：search_vector() 用相对归一化（/ max_s），max_s=0.08 也会变成 1.0
    修复：FAISS_MIN_QUALITY = 0.10 绝对门控
          原始最高余弦 < 0.10 → 返回 {} → API 返回空列表
          search_bm25() 同理：max_s <= 0 直接返回 {}

  P5 BM25 专有名词丢失：GPT 改写破坏关键词索引
    现象：搜 "GraphSAGE" → BM25 整个语料库无命中 → 退化为纯 FAISS 搜索
    根因：BM25 语料来自 GPT 提取的 methodology 字段
          "We apply GraphSAGE on OGB-Arxiv" → "uses graph sampling method on citation dataset"
    修复：build_corpus() 加入 abstract 字段（排在 research_question 之前）
          保留 GraphSAGE、BERT-large、SQuAD 等专有名词供精确匹配

── 修改的文件 ──
  scripts/db.py           — new_columns 加 abstract 字段迁移
  scripts/build_index.py  — is_cs_paper() / _CS_KEYWORDS / build_text() 优先摘要
  scripts/hybrid_search.py — build_corpus() 加摘要 / FAISS_MIN_QUALITY 阈值
                             / search_vector() 绝对门控 / search_bm25() 空返回
                             / rerank_with_cross_encoder() Cross-Encoder 精排

── 测试结果 ──
  tests/test_pipeline_fixes.py: 32/32 通过（0 失败，3 DeprecationWarning 忽略）
    TestP1DomainFilter        7/7   领域过滤（is_cs_paper）
