## 零-A、Pipeline 质量修复（2026-04-06）

> 背景：在小规模语料库（164 篇）上发现搜索 Pipeline 存在五个系统性缺陷，逐一修复并补测试。

### 问题 → 根因 → 修复 对照表

| # | 问题 | 根因 | 修复文件 | 修复方式 |
|---|------|------|---------|---------|
| P1 | 搜 GNN 返回流体力学论文 | 上传时无领域校验，向量空间被污染 | `build_index.py` | 新增 `is_cs_paper()` + `_CS_KEYWORDS` 白名单，建索引时过滤非 CS 论文 |
| P2 | Embedding 信息量不足 | `build_text()` 用 GPT 压缩后的短字段（300词→60词），专有名词泛化 | `build_index.py` | `build_text()` 优先用 `abstract` 原始摘要；无摘要时降级 GPT 字段 |
| P3 | 无精排，召回即返回 | Bi-Encoder 训练目标是快速召回，不是精确排序 | `hybrid_search.py` | 新增 `rerank_with_cross_encoder()`，用 cross-encoder/ms-marco-MiniLM-L-6-v2 精排 top-50 |
| P4 | 归一化分数误导（0.483 看起来还行实际垃圾） | 相对归一化让最高原始分 0.08 也变成 1.0 | `hybrid_search.py` | 加 `FAISS_MIN_QUALITY=0.10` 门控，原始最高分 < 0.10 直接返回空 |
| P5 | BM25 关键词匹配失效 | GPT 改写摘要后专有名词丢失（GraphSAGE→"graph sampling method"） | `hybrid_search.py` | `build_corpus()` 加入 `abstract` 字段，保留专有名词供关键词索引 |

**P3 — hybrid_search.py**
```python
def rerank_with_cross_encoder(query, candidates, text_field="text"):
    ce = _get_cross_encoder()   # 延迟加载，首次 ~300ms
    if ce is None:
        return candidates       # 降级：保持 Bi-Encoder 顺序
    scores = ce.predict([(query, c[text_field]) for c in candidates])
    for c, s in zip(candidates, scores):
        c["cross_encoder_score"] = float(s)
    return sorted(candidates, key=lambda x: -x["cross_encoder_score"])
```

### 教训

> **最大的问题不是算法是数据。** GraphSAGE 专有名词丢了、摘要被压缩了、领域外论文混进来了——用最好的 Rerank 模型也救不回来。先清洗数据、让 Embedding 编码原始文本，再加阈值兜底，最后才是 Cross-Encoder。**Pipeline 每个环节都不能跳，跳了就是给下游挖坑。**

## 二、各技术组件说明与参考来源

### 1. FAISS — 向量相似度搜索

**当前用途**：论文语义检索（IndexIDMap2 + text-embedding-3-small）

**扩展方向**：单机 FAISS → 分布式向量数据库（Milvus）

**参考来源**：
- **论文**：Johnson J, Douze M, Jégou H. *Billion-scale similarity search with GPUs*. IEEE Transactions on Big Data, 2019.
  - 搜索标题可在 arXiv 找到：arXiv:1702.08734
- **开源项目**：https://github.com/facebookresearch/faiss
- **Milvus（分布式向量库）**：https://github.com/milvus-io/milvus

---

### 2. Kafka — 行为事件总线

**当前问题**：`record_behavior()` 同步写 SQLite，高峰阻塞请求链路。

**改进**：用户行为（浏览/点赞/搜索）produce 到 Kafka，Consumer 批量异步落库，热度分异步更新。

**参考来源**：
- **原始论文**：Kreps J, Narkhede N, Rao J. *Kafka: A Distributed Messaging System for Log Processing*. NetDB Workshop, 2011.
  - 可在 LinkedIn Engineering Blog 找到
- **开源项目**：https://github.com/apache/kafka
- **Go 客户端**：https://github.com/segmentio/kafka-go
- **实践案例**：LinkedIn 使用 Kafka 处理每天超过 1 万亿条消息（官方博客：engineering.linkedin.com）

---

### 3. Redis — 多模式缓存

**三种用法**：
- `ZSet`：实时热度榜，`ZINCRBY` 增量更新，`ZREVRANGE` 取 Top-N，O(log N)
- `Hash`：论文详情缓存，TTL=1h，写操作后 DEL 失效
- `String`：搜索结果缓存，key=`search:{query_hash}:{mode}`，TTL=5min

**参考来源**：
- **官方文档**：https://redis.io/docs
- **开源项目**：https://github.com/redis/redis
- **Sorted Set 实现原理**：Redis 内部用跳表（Skip List）实现 ZSet，参见 Redis 作者 antirez 博客

---

### 4. gRPC — 服务间通信

**用途**：Go Gateway → Python Search/Rec Service，替代 HTTP，协议更紧凑，长连接复用，性能约为 HTTP/JSON 的 3-5 倍。

**参考来源**：
- **官网**：https://grpc.io
- **开源项目**：https://github.com/grpc/grpc
- **Go 实现**：https://github.com/grpc/grpc-go
- **性能对比论文**：Gutierrez J et al. *Performance Evaluation of RESTful and gRPC Protocols*. IEEE Access, 2021.

---

### 5. Go + Gin — 高并发 API 网关

**为什么替换 FastAPI**：Python GIL 限制真正并发，Go goroutine 调度开销极低，单机可支撑 10 万并发连接。

**参考来源**：
- **Gin 框架**：https://github.com/gin-gonic/gin
- **Go 官方**：https://golang.org
- **WebSocket 库**：https://github.com/gorilla/websocket
- **并发模型参考**：Go 语言设计者 Rob Pike 的演讲 *Concurrency is not Parallelism*（可在 go.dev/talks 找到）

---

### 6. Prometheus + Grafana — 可观测性

**埋点指标**：
- `search_latency_seconds{mode="hybrid"}` — p50/p99 搜索延迟
- `cache_hit_total{type="paper_detail"}` — Redis 命中率
- `kafka_consumer_lag{topic="user-behaviors"}` — 消费积压
- `faiss_index_search_ms` — 向量检索耗时
- `active_websocket_connections` — 实时连接数

**参考来源**：
- **Prometheus**：https://github.com/prometheus/prometheus
- **Grafana**：https://github.com/grafana/grafana
- **Go 客户端**：https://github.com/prometheus/client_golang

## 四、最优先的一个改动（当前可立即做）

`hybrid_search.py` 中 `search_vector()` 每次请求都执行：

```python
index = faiss.read_index(INDEX_API)  # 每次从磁盘读！
```

改为模块级变量，启动时加载一次：

```python
# 模块顶部，启动时执行一次
_faiss_index = faiss.read_index(INDEX_API)

def search_vector(query_vec, top_k):
    scores, ids = _faiss_index.search(query_vec, _faiss_index.ntotal)
    ...
```

**效果**：磁盘 I/O 从每次请求变为仅启动时一次，搜索延迟从 ~200ms 降至 ~5ms。
